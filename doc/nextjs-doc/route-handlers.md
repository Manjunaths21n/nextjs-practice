Route Handlers define custom HTTP request handlers with the Web `Request` and `Response` APIs. They are the App Router equivalent of Pages Router API Routes; a project does not need to use both.

## Convention and methods

Create a `route.ts` or `route.js` file anywhere under `app`. Export functions named for the HTTP methods you support:

```ts
// app/api/route.ts
export async function GET(request: Request) {
  return Response.json({ ok: true })
}
```

Supported methods: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, and `OPTIONS`. An unsupported method receives `405 Method Not Allowed`. For additional helpers, Next.js provides `NextRequest` and `NextResponse`.

## Caching

- Route Handlers are **not cached by default**.
- Without Cache Components, a `GET` handler can opt into caching with route configuration such as `dynamic = 'force-static'`. Other HTTP methods are not cached.
- With Cache Components, a `GET` handler can be prerendered when it avoids runtime/uncached data. Use `'use cache'` in a helper function to cache data; it cannot be placed directly inside the handler body.

## Route resolution

- A Route Handler is a low-level routing primitive; it does not participate in layouts or client-side page navigation.
- A `route.ts` and `page.tsx` cannot claim the same route segment. Put APIs under a distinct path such as `app/api/`.
- A Route Handler takes over all HTTP methods for its route.
- Special metadata handlers such as `sitemap.ts` and `opengraph-image.tsx` are static by default unless they use request-time data or dynamic configuration.

## Typing route context

Use the generated global `RouteContext` helper for typed dynamic params. Types are generated by `next dev`, `next build`, or `next typegen`.

```ts
export async function GET(
  _request: Request,
  ctx: RouteContext<'/users/[id]'>
) {
  const { id } = await ctx.params
  return Response.json({ id })
}
```
